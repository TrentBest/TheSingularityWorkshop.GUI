# Testing Strategy

GUI engineering has separate correctness questions. Passing one layer's tests does not establish correctness at every layer.

1. **Model correctness** — does Core represent the intended semantic structure?
2. **Adapter correctness** — does an adapter translate that structure according to its supported contract?
3. **Platform correctness** — does the target framework behave as intended?
4. **Artifact correctness** — does a checked-in generated visual still match the output of its generator?
5. **Architectural correctness** — do source dependencies and documented boundaries agree with the design?

## Core contract tests

Core tests run without a UI platform. They are the foundation for adapter work and should cover the invariants actually owned by Core, including recursive composition, identity, snapshot behavior, property isolation, child ordering, coordinate primitives, and invalid input. Current regression coverage also rejects null child entries and exercises direct/indirect builder-cycle rejection.

A green Core test suite does **not** prove that a native adapter renders correctly or that proposed execution/spatial contracts have been implemented.

## Adapter contract tests

Adapters should preserve the semantic properties that their contracts promise, while being free to use different native representations.

A shared semantic case might describe:

```text
Panel(root) -> Button(save) -> Text(Save)
```

The relevant comparison is hierarchy, identity, semantic kind, text, child order, and any other explicitly specified invariant—not equality of WPF controls and browser render-tree nodes.

Current status is tracked in [ROADMAP.md](../ROADMAP.md). Focused Blazor and SVG contract tests cover adapter-specific invariants. The shared conformance project runs a common tree through Blazor and SVG and compares selected observable properties such as identity, child ordering, and text preservation. This is an initial, narrow fixture, not broad cross-platform conformance coverage.

The WPF suite runs on Windows and tests the WPF renderer's current supported surface, including nested hierarchy/order, text, supported dimensions and spacing, colors, typography, alignment, horizontal `Row` composition and orientation overrides, semantic `isEnabled`, host-owned `resource:` theme keys, null-root rejection, unknown-kind fallback, duplicate-ID rejection, the 256-edge depth guard, and exact semantic-ID preservation through a WPF-specific attached property when `FrameworkElement.Name` cannot represent the ID. See [Platform Adapters](PLATFORM_ADAPTERS.md) for the distinction between this evidence and full adapter parity.

## SVG adapter tests and generated gallery

The SVG contract suite checks the serializer's supported behavior, including coordinate mapping, geometry, transforms, XML escaping, reusable definitions, filters, accessibility-related output, explicit animation nodes, invalid inputs, root-node identity as the SVG document ID, generated-ID collision rejection, and the 100,000-node pre-serialization guard. Run it with:

```sh
dotnet test tests/SVG.Tests/TheSingularityWorkshop.GUI.SVG.Tests.csproj --configuration Release
```

The gallery at [assets/svg-adapter-gallery.svg](assets/svg-adapter-gallery.svg) is generated by `samples/SvgGallery/Program.cs`. The documented workflow regenerates it and compares the result with the checked-in snapshot. That proves the snapshot matches the sample output under that workflow; it does not prove every visual feature is supported by every SVG viewer, nor that the SVG is a GPU-rendered scene.

For the gallery, review both the generator and its output. A passing byte-for-byte snapshot check detects drift from the generator, not a conceptual mistake shared by the generator and snapshot.

## Boundary-focused regression examples

Use these focused tests when changing the corresponding contract:

- **Core tree safety:** `tests/Core.Tests/GuiBuilderTests.cs` covers null child entries and direct/indirect cycles. A renderer must not be the first place a malformed Core tree is discovered when Core can reject it deterministically.
- **SVG artifact identity and resource bounds:** `tests/SVG.Tests/SvgGuiRendererTests.cs` covers root identity, generated accessibility-ID collisions, and rejecting an oversized scene before serialization. The limit is a safety bound, not a guarantee that building an arbitrarily large tree is cheap.
- **WPF host boundaries:** `tests/WPF.Tests/WpfGuiRendererConformanceTests.cs` covers horizontal rows, enabled state, and host-owned dynamic theme resources. A resource key is supplied by the host; it is not a GUI.Core-owned palette, and `isEnabled` is presentation state rather than authorization.
- **Executable integration proof:** [FSM-driven bounded oscillator](../samples/demonstrations/recipes/07-fsm-driven-oscillator.md) demonstrates FSM_API state transitions flowing into GUI Core and a static GUI.SVG artifact. Its trace and SVG structure are asserted in CI; it does not prove live animation or universal SVG viewer behavior.

The source-derived UML workflow also verifies that generated Markdown retains the Workshop moniker/footer and that generated source inventory excludes build-artifact paths. That is a generation-integrity check, not proof that every type has a complete human-authored use case.

## Platform tests

Platform-specific tests should verify behavior that cannot be established by Core tests alone, such as native WPF configuration, Blazor render output, event wiring, resource lifetime, and accessibility integration. State which platform and behavior a test covers. WPF tests require a Windows runner; a Linux cross-targeting build is not a substitute for running the native tests.

## CI execution matrix

The authoritative package workflow is [`.github/workflows/package.yml`](../.github/workflows/package.yml). Test execution is explicit; solution membership alone does not prove that a test project ran.

| Check | Runner | Explicit project or action | Evidence scope |
|---|---|---|---|
| Core tests | `ubuntu-latest` | `tests/Core.Tests/TheSingularityWorkshop.GUI.Core.Tests.csproj` | Core model invariants |
| Blazor tests | `ubuntu-latest` | `tests/Blazor.Tests/TheSingularityWorkshop.GUI.Blazor.Tests.csproj` | Blazor renderer behavior |
| SVG tests | `ubuntu-latest` | `tests/SVG.Tests/TheSingularityWorkshop.GUI.SVG.Tests.csproj` | SVG renderer/serialization contract |
| Shared adapter conformance | `ubuntu-latest` | `tests/Adapter.Conformance.Tests/TheSingularityWorkshop.GUI.Adapter.Conformance.Tests.csproj` | Shared fixture for Core, Blazor, and SVG; does not cover WPF |
| WPF renderer tests | `windows-latest` | `tests/WPF.Tests/TheSingularityWorkshop.GUI.WPF.Tests.csproj` | Native Windows/WPF behavior |
| WPF packed-consumer check | `windows-latest` | Generated `net8.0-windows` consumer restored only from packed Core/WPF archives | Exercised package-only consumer path, not broad API parity |

The workflow also builds WPF on Linux with `EnableWindowsTargeting=true`. That build is separate from native Windows test execution. The guarded `publish_nuget` job depends on both package and WPF jobs and remains hard-disabled until explicit owner authorization and Sith compliance are satisfied.

### Test projects omitted from the solution manifest

The current `TheSingularityWorkshop.GUI.slnx` includes Core, Blazor, and SVG test projects, but omits `tests/WPF.Tests` and `tests/Adapter.Conformance.Tests`. These tests are **not skipped**: the package workflow invokes both projects directly, with WPF tests on Windows.

For now, keep these platform/conformance projects explicitly orchestrated by CI rather than silently changing solution-derived build and inventory scope. Before adding them to the solution manifest, verify the solution-derived UML workflow's intended product-project boundary. Revisit this decision if local solution builds are expected to include every CI test project.

## Evidence and status discipline

Use the following rules when documenting correctness:

- **Implemented:** visible in current source; cite the relevant implementation surface where practical.
- **Tested:** covered by a named test or repeatable verification command.
- **CI-verified:** the relevant workflow completed successfully for the stated commit.
- **Specified:** behavior is documented, but no implementation claim is implied.
- **Proposed / unresolved:** design work remains; do not describe it as an available feature.

A passing workflow is evidence for the checks it actually ran—not proof that all documentation, all links, every platform, or the entire architecture is correct. Roadmap status is useful context, but should be kept aligned with current projects and tests.

## Current limits

The richer execution-host model, capability negotiation, broad shared adapter conformance, and many spatial invariants remain design targets. See [Next Contract Surface](NEXT_CONTRACT_SURFACE.md), [GUI Spatial Contracts](GUI_SPATIAL_CONTRACTS.md), and [ROADMAP.md](../ROADMAP.md) before treating those concepts as current Core APIs.
