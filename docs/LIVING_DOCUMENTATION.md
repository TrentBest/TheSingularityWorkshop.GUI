# Living Documentation

A **living picture** demonstrates something about the thing it describes. It may make meaningful state, sequence, scale, cause, or effect observable to a reader. When useful, narration should explain what is happening and why, including for people who listen rather than watch.

A living picture must be honest about its evidence. It may be a concept animation, a source-derived diagram, an artifact produced by the real framework, or a capture from a running host. Label which kind it is and never imply that an authored concept proves runtime behavior.

## Evidence classes

- **Generated output:** produced by a named sample/generator from a known source revision.
- **Source-derived diagram:** projected from parsed or compiled source; state whether analysis is syntax-only or compiler-semantic.
- **Runtime observation:** captured from a running application or model, with the driver, mutation boundary, and observed revision identified.
- **Concept illustration:** authored to explain an idea, not evidence that the illustrated behavior is implemented.

## Examples in GUI

- The SVG adapter gallery is generated by the actual SvgGallery sample and checked against the committed asset by the package workflow.
- The demonstration recipes render finite records from Physics, including seeded points and parameterized Mandelbrot classifications. Their output is checked against those records rather than recomputed in GUI.SVG.
- Source-derived UML is a staging vertical slice: generation and structure are checked in CI, but generated per-type pages are not yet promoted into the keeper branch.
- The fox/sheepdog scene is built through the real GUI model and SVG adapter, but its checked-in asset is not currently guaranteed to be byte-identical to a fresh generation.
- Future console-driven or host-driven visualizations may observe a mutable model, but they must name the model, driver, mutation contract, and refresh behavior. SVG markup alone is not a reactive view.

## Rules for truthful visuals

1. Identify the model or source that owns the fact being shown.
2. Link the source builder, renderer, test, workflow, or run record that supports the claim.
3. Distinguish implementation from proposal and generated output from authored concept art.
4. State important non-claims: for example, SVG animation is not proof of a live FSM transition or GPU execution.
5. Regenerate from source where possible; review unexpected diffs instead of hiding drift.
6. Treat XML validity as necessary but insufficient: visual bounds, text legibility, accessibility, and viewer behavior are separate checks.
7. Prefer reduced-motion-friendly, accessible explanations and avoid using color as the only signal.
